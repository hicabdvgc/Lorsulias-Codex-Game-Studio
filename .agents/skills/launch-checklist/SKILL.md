# External Launch Readiness

Invoke `$launch-checklist [YYYY-MM-DD|dry-run]`. Preserve explicit invocation policy.

Read root instructions and the shared contracts linked below. Carry existing bounded task authorization
through saves; clarify consequential unresolved choices. Reread shared files before writes, preserve
concurrent changes and stable identities, and read back promised outputs. Required independent review
and actual human evidence survive executor changes and review-depth choices. Report missing evidence
and preserve partial work; a saved document never establishes approval or execution.

Read `.codex/docs/release-and-operations.md`, `.codex/docs/execution-and-evidence.md`,
`.codex/docs/progression.md`, live `docs/technical-preferences.md`, and the selected release context.
Apply the shared candidate identity, evidence, verdict, write and external-action contracts.

## Select scope

Require one valid calendar date or dry-run. Resolve the release/candidate/platforms from explicit
context or one validated reference; ask when ambiguous. Reject dates earlier than today for this launch-planning route and resolve the
intended launch date. Never invent a launch date for dry-run.

Read production/releases/RELEASE_CHECKLIST.md and the exact relevant internal report. Assess applicable
store/package distribution, legal/licensing/certification, system requirements, languages/accessibility,
infrastructure/recovery, support and player communication. Use actual configured platforms/services;
an offline distribution need not have storefronts, servers, analytics or marketing campaigns.

Source current external obligations from official applicable documentation; inaccessible platform or
external-service evidence remains NOT VERIFIED. Repository absence does not prove an external failure.
Distinguish actual publication from prepared drafts. Do not require a success announcement to have been
published before launch. A selected communication plan can be ready while publication remains pending.

Production code/content scans, if relevant, resolve real roots and exclude generated/vendor/fixture
content. Markers and suspected development values are findings requiring assessment, not automatic
release failures. Report suspected secrets by safe category/path, never by copying values.

## Assess and hand off

Use the shared report identity and item schema. Required failures or unavailable evidence yield
LAUNCH BLOCKED; all required checks satisfied with advisory gaps yield CONCERNS; otherwise LAUNCH READY.
Sign-offs name actual responsibilities/evaluators and evidence, with required independence/human checks.
No mandatory director roster, universal count, numeric budget or checklist shape overrides applicability.

Compare an explicitly identified comparable earlier assessment, or label first baseline. For dry-run,
show the complete evidence-annotated assessment and verdict with `not persisted — not valid sign-off
evidence`; write nothing. For a requested dated assessment, save
production/launch/launch-checklist-[date].md, preserving unrelated date collisions as described in the
shared contract. Return exact saved path, identity, verdict and blocking/advisory findings to
`$team-release` and applicable `$gate-check final-acceptance`. Save verification never authorizes release.
