# Guided Studio Start

Invoke `$start` with no arguments.

Read root instructions and the shared contracts linked below. Carry existing bounded task authorization
through saves; clarify consequential unresolved choices. Reread shared files before writes, preserve
concurrent changes and stable identities, and read back promised outputs. Required independent review
and actual human evidence survive executor changes and review-depth choices. Report missing evidence
and preserve partial work; a saved document never establishes approval or execution.

Read `.codex/docs/workflow-catalog.yaml`, `.codex/docs/progression.md`, live
`docs/technical-preferences.md` and relevant current artifacts. The four section IDs are
conceptualization, development-schematics, pre-implementation, implementation. Report the declared
section separately from available outcomes and missing prerequisites. Preserve unknown/legacy stage
values until their interpretation is explicitly resolved; counts/existence cannot establish progress.
Story Status fields own progress; selected sprint YAML is derived. Active scope needs an explicit or
unique existing reference, never modification time. There is no review-mode file to create.

## Orient and route

Inspect the current task and available concept, BREAKDOWN, FRAMEWORK, resource/tool contracts,
architecture, work items and supplied human findings. If the user already gave a clear objective,
continue that context. Otherwise ask whether they have no idea, a vague idea, a clear concept, or
existing work, and tailor the next activity. Do not force a returning user through a creative survey.

- No idea/vague idea: offer `$brainstorm open` or the supplied hint and reference-study guidance.
- Clear concept: support the developer in writing CONCEPT; then use preliminary `$map-systems`.
- Existing work: use `$adopt` for compatibility and `$project-stage-detect` for outcome gaps.

Explain only the relevant next segment of the catalog: developer CONCEPT -> preliminary BREAKDOWN ->
framework principles -> full BREAKDOWN/preliminary FRAMEWORK -> system GDDs -> full FRAMEWORK ->
architecture/Accepted ADRs/CONTROL -> resources/tools/UX -> slice -> prepared work and required reviews ->
hard slice gate -> final milestones -> actual evaluation -> final acceptance/release. Prototypes and
art direction are conditional capabilities. Engine research/selection cannot replace earlier outcomes.

## Optional declared section and handoff

With an explicit section choice and authorization to initialize it, write the first nonempty line of
production/stage.txt using its canonical ID. Preserve an existing valid declaration unless the task
explicitly changes it through the applicable progression process. Missing/invalid data can remain
unconfigured; orientation does not require a write or automatic gate. Never initialize from file counts.

Present the next activity, required human/manual work, usable inputs and unresolved prerequisites.
Invoke another skill only within the current request and its invocation policy. COMPLETE means the
user has a usable orientation/handoff; identify configuration actually saved versus left unchanged.
