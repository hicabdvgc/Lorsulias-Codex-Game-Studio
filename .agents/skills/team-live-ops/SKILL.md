# Live Operations Planning

Invoke `$team-live-ops [season name|event description]`.

Read root instructions and the shared contracts linked below. Carry existing bounded task authorization
through saves; clarify consequential unresolved choices. Reread shared files before writes, preserve
concurrent changes and stable identities, and read back promised outputs. Required independent review
and actual human evidence survive executor changes and review-depth choices. Report missing evidence
and preserve partial work; a saved document never establishes approval or execution.

Read `.codex/docs/release-and-operations.md`, `.codex/docs/execution-and-evidence.md`,
`.codex/docs/progression.md`, live `docs/technical-preferences.md`, and the selected release context.
Apply the shared candidate identity, evidence, verdict, write and external-action contracts.

## Scope and responsibilities

Confirm that seasonal/event work is actually requested for this game. Resolve intended player experience,
duration/cadence if selected, content scope and actual existing designs/FRAMEWORK/resource/tool contracts.
Ordinary post-launch maintenance need not use live-service systems. Preserve accepted canon and decisions.
Choose only relevant tasks and qualified available executors under current delegation authorization.

## Produce the relevant parts of the plan

1. Build the season/event brief: goals, audience, content, dependencies, selected timing and evaluation.
2. Develop narrative theme/hooks/lore connections when applicable, with actual writers and canon sources.
3. For economy/rewards, use supplied economy rules, units and constraints. Pricing/currency health is
   unassessed without those rules; a non-pricing outline can remain an explicit draft. Premium tracks,
   random rewards, pity mechanics and storefront rotations apply only when selected.
4. For analytics, define meaningful questions, data/events, comparison basis and evaluation plan. Do
   not invent targets or claim instrumentation/dashboards exist. Telemetry and A/B tests are optional.
   Reconcile final rewards/cadence with selected measurement needs, documenting gaps and privacy choices.
5. Write applicable content and resource preparation/integration requirements. Text specifications are
   drafts, not implemented/usable game resources.
6. Draft factual player communications and selected cadence. No universal urgency/FOMO campaign or
   automatic posting. Use actual policy/voice and supplied dates.

## Review, save and hand off

Review applicable economy and communication choices against actual project policies. A known violation
blocks acceptance/production until revised. Missing policy is explicitly unreviewed and blocks only
when that policy/evaluation is a project prerequisite; never claim fairness/privacy compliance from
missing evidence. Preserve useful authorized drafts, marked with unresolved decisions.

Use design/live-ops/seasons/S[N]_[slug].md for the plan, with _analytics.md and _comms.md siblings only
when those outputs are in scope. Retain supplied season identity; otherwise inspect existing IDs and
propose a collision-free number/slug. Reread before writes to detect concurrent allocations. Do not
overwrite another event. Assign one writer per file and verify all promised saves.

Return scope, plan state, actual outputs, applicable checks and open production decisions. COMPLETE
means the requested plan is usable with required decisions/evaluation resolved; DRAFT or BLOCKED
identifies incomplete required work. It never means content was built, playtested or deployed.
Route implementation through framework/epic/story procedures, optional sprints within defined milestones,
and release coordination when ready. Do not send a season plan to system-GDD-only design review.
