# Team Narrative

Invoke `$team-narrative [narrative content description]`. A target is required; missing target returns usage
without writes or delegation. Reject unknown control flags and ambiguous targets.

## Responsibility and evidence

Select only work needed by the request. Follow the current environment's delegation
policy. Available qualified people/agents can perform the responsibilities below;
roles do not require a fixed team. Identify self-review; preserve required independent
review and actual human evidence under `.codex/docs/review-workflow.md`.

Use existing bounded task authorization. Ask about consequential unresolved choices
or material scope expansion, without per-phase approval prompts. Before concurrent
work, assign one writer per output and keep shared sources read-only for other
executors. The current agent can write within its assigned scope. Re-read shared
records before saving and preserve concurrent changes and stable identities.

Read `.codex/docs/resource-preparation.md`; connect loose material and design outputs
to root RES_TYPE.md, relevant resource_templates/TYPE_TEMP definitions and res_lib/
when defined. Initial content design may record unresolved contracts. Prepared
resources and runtime integration require their actual contracts and evidence.
Use `.codex/docs/tool-development.md` only for a demonstrated unmet tooling need.

## Recovery and result

Read back every promised saved output before reporting delivery. Preserve completed
work if an executor fails. Assign the missing work to a qualified available executor
or mark the dependent activity BLOCKED; never invent the missing result. Report
selected scope, output paths, actual evaluation and remaining dependencies.
COMPLETE applies only to the requested deliverable when all its requirements are
met. A draft can be delivered as a draft; canon acceptance, implemented behavior,
produced media and human/play evaluation require their separate evidence.

## Context and output boundary

Resolve the requested scene, character or narrative area from explicit references
and existing documents. Ambiguous identity requires clarification before writing.
Read developer CONCEPT, relevant GDD/FRAMEWORK behavior, canon and voice profiles,
selected localization/accessibility needs and existing output paths. Choose concrete
paths within the established narrative organization; no genre or story arc is assumed.

## Work sequence

1. **Narrative direction** — identify the story/player purpose, characters and motives,
   emotional/pacing targets and lore dependencies. A narrative-director can support this.
2. **World foundation and writing** — a world-builder checks relevant world rules,
   factions, history and proposed canon; a writer drafts the requested dialogue,
   descriptions or lore using the available voice/context evidence. Canon-dependent
   text stays provisional until consequential canon choices are settled. Do not
   invent character limits; use selected layout/TYPE_TEMP constraints.
3. **Presentation and level integration, when needed** — art and level expertise can
   specify visual storytelling, triggers, discovery points and pacing. A dialogue-only
   task need not create levels, art direction or unrelated lore.
4. **Consistency review** — check final text against voice, canon, world rules,
   system state and relevant level behavior. Mysteries need defined hidden facts only
   where dependent design requires them; unresolved ambiguity can be intentional.
5. **Relevant polish** — inspect string identities, placeholders, selected locales,
   layout constraints and cultural questions. Use qualified human evaluation when
   required. Recheck affected content after corrections; earlier review does not
   cover subsequently changed text.

Save the requested narrative outputs within the authorized boundary. Record the
selected canon status (Established / Provisional / Under Review) without promoting
new facts automatically. Existing entity facts remain owned by their source/registry.
`$localize extract` can prepare selected string resources; engine trigger execution
and `$dev-story` support are available. Do not claim runtime narrative behavior
from prose or a planned trigger list.
