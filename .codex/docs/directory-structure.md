The existing `design/`, `docs/`, `assets/`, `src/`, `tests/`, `tools/`,
`production/`, and `prototypes/` organization is retained. Actual code and test
roots will follow the selected engine. Prototype retention is a project decision.

## Research and resource interfaces

Root-level `game_ref/` contains individual study Markdown files and associated
evidence folders, using `.codex/docs/templates/reference-game-study.md`.
The developer supplies actual human observations; research keeps sources distinct
from interpretation.

The workflow also requires `RES_TYPE.md`, per-type `TYPE_TEMP` definitions
in `resource_templates/`, loose source material, `res_lib/`, and `tools_lib/`.
These four locations are studio-root paths. Internal formats, loose-source locations and import destinations are selected per type. Use [resource preparation](resource-preparation.md) and [tool development](tool-development.md); distinguish authoritative resources from derived imports. Game-specific contents remain outputs of later use.

## Maturity, decisions, and dependencies

Identify preliminary/full BREAKDOWN and FRAMEWORK states explicitly in those
documents when authored. Use the systems-index and development-framework
templates under `.codex/docs/templates/`. Initial system GDD authoring uses full BREAKDOWN and preliminary
FRAMEWORK; completing FRAMEWORK follows the initial designs. Resource schemas
enter the later integration reviews. A task creating a resource or tool needs
its specification and inputs; the new resource/tool is its output.

Retain the integer `Manifest Version:` convention for CONTROL. Increment it when
governing rules change; record the version used by dependent work. A date alone
cannot distinguish same-day revisions. ADR statuses remain Proposed, Accepted,
and Superseded; acceptance and supersession require the relevant decision.
Retain stable existing identifiers and supported statuses across installed producers
and consumers. Game-specific schemas and populated registries are authored during use.

Keep a single editable authority for each artifact. Update its affected writers,
readers, templates, and checks together when its interface changes.

## Work preparation and test evidence

`production/epics/[epic]/EPIC.md`, `story-NNN-[slug].md` and the existing index
retain stable identities. Story Status is authoritative; `production/sprint-status.yaml`
derives the selected sprint's statuses. Planning documents live in production/sprints/;
retrospectives use production/retrospectives/. `$define-milestones` authors the
single MILESTONE.md after the hard gate, with earlier incomplete drafts identified.
QA plans use `production/qa/qa-plan-[scope]-[date].md`; manual evidence uses
production/qa/evidence/. Automated tests/reports use selected runner locations.
See [work preparation](work-preparation.md) and [root resolution](code-root-resolution.md).
The story-status helper is an explicit read-only observer, without lifecycle registration.

The optional [project-coherence observer](project-coherence.md) compares live preferences
with an explicitly named engine project. The [pitch template](templates/pitch-document.md)
supports a requested presentation without adding a workflow gate.

## Execution records

New playtest reports use `production/playtests/`; QA plans, smoke reports and sign-offs use `production/qa/`, with criterion evidence under its `evidence/` directory or existing specific paths. An existing slice report or `prototypes/[concept-slug]-vertical-slice/REPORT.md` records the slice run and separate hard-gate handoff. `production/stage.txt` declares a canonical catalog section when a game has selected one; it is not outcome evidence. `production/integration-runs/` holds ignored operational journals for actual Git integration. These are outputs of later game work, not fabricated skeleton records.
