# System Design Documents

Follow the GDD template for applicable content. CONCEPT and BREAKDOWN have their
own roles and must not be mistaken for system GDDs during discovery.

Each system needs an identifiable boundary, behavior, interactions, applicable
rules, unresolved questions and evaluation methods. Formulas state variables,
units, ranges and boundary behavior. Explain dependency direction and shared
ownership; keep the affected consumers consistent when an interface changes.

Describe how the system supports framework additions/modifications and what
resources it needs. Future schemas remain pending during initial design. Human
experience targets are design intentions until actual play evidence exists.

Preserve the developer's CONCEPT. Carry existing task authorization through
drafting, revisions and relevant registry/BREAKDOWN updates; ask about unsettled
design choices. Independent design review remains distinct from author self-check.
